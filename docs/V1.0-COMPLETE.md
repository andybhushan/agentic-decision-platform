## 1. Mission · Vision · Goals

### Mission
Run claim operations agentically, end-to-end — from FNOL through Damage Assessment, Fraud Investigation, and Settlement — with every decision made by a named agent, every output grounded in cited sources, every consequential moment gated by a human-in-the-loop. Auditable, replayable, accountable.

### Vision
The platform under any frontier firm's vertical operations. Meridian P&C Auto is Client Zero. The boundary between platform and use case is mechanical — banking proved it with a 2-agent stress test (zero platform changes). Healthcare, public sector, supply chain are sibling folders under `usecases/`. The platform is Microsoft-native, customer-facing, single-industry-deep — distinguished by depth, not breadth.

### v1.0 Goals (all delivered)
1. **Honest IQ federation.** Three independent context sources — Foundry IQ (Azure AI Search), Fabric IQ (Lakehouse + aggregation primitives), Work IQ (synthetic-deterministic + real Microsoft Graph code) — all running on real Microsoft services, all citing in production traces.
2. **Full Meridian lifecycle.** Four Digital Workers covering FNOL → Damage → Fraud → Settlement. Three HITL gate types (confidence, field-value, mandatory-band). 19 knowledge docs governing reasoning.
3. **Demonstrable agnosticism.** Banking stress test in its own folder. Zero Meridian intent names, table names, or tool IDs in `platform/src/`. Boundary enforced at CI level.
4. **Stakeholder-grade demo surface.** Operator console with 8 buttons across 4 DWs and live SignalR tail; impressive docs portal SPA at `/docs` with mission, system architecture, workflow, deployment map, and 16 ADRs.

## 2. The Three-Source Federation (L5 Trio)

Each agent step calls `ContextRouter`, which fans the request to three sources and merges fragments. Packages declare per-intent `sourceBindings` as named primitives — zero industry coupling in platform code.

### Foundry IQ — Azure AI Search
- Resource: `srch-adp-v1` (eastus). Index `adp-knowledge` with 21 markdown docs (19 insurance + 2 banking), 3072-d embeddings via `text-embedding-3-large`.
- Industry-filtered queries: an `industry` field on each doc (derived from frontmatter `domain`); the source adds `industry eq '{value}'` to every OData filter. Eliminates cross-industry vector bleed (banking agents never see Meridian docs).
- One primitive: semantic vector search over the package's industry's knowledge.

### Fabric IQ — Microsoft Fabric Lakehouse
- Resource: workspace `adp-v1` (capacity `offeringsfabric001`), Lakehouse `adp`. Five Delta tables: `dim_policyholder`, `dim_vehicle`, `fact_claims` (Meridian); `dim_borrower`, `fact_loan_applications` (banking).
- Queried via the Lakehouse SQL analytics endpoint with `Microsoft.Data.SqlClient` + AAD auth (Function MI has Viewer on the workspace).
- **Eight named primitives** packages can bind to:
  - Row-level (P&C-shaped): `policyholder-history`, `similar-claims`, `vehicle-history`
  - Row-level (schema-aware, Track 5): `entity-history` — templated query off `digitalWorker.schemaBinding`; banking activates against `fact_loan_applications` + `dim_borrower`
  - Aggregation rollups (Track 1 — ADR-0014): `severity-distribution-by-state`, `hour-of-day-concentration`, `state-loss-ratio`, `incident-type-mix-by-state`
- Per ADR-0014, this is honest "Fabric IQ" at the Lakehouse default-semantic-model level; full Power BI semantic model with named DAX measures is a v1.5 enhancement.

### Work IQ — synthetic (default) + Microsoft Graph (code-ready)
- Default: `WorkIqSource` — deterministic synthetic fragments per claim (Teams threads, calendar signals, SharePoint photo threads). Reproducible demos.
- Track 3 (ADR-0015): `MicrosoftGraphWorkIqSource` — raw HTTP against Graph endpoints (`/me/messages`, `/me/drive/root/search`, `/me/calendarView`). Delegated scopes only — local CLI opts in; cloud Function MI stays on synthetic (admin consent would be required on the IBM tenant).
- Activation: `WORKIQ_BACKEND=graph` env var + user-tenant seeding (Outlook emails / OneDrive files / calendar entries containing claim IDs).

## 4. The Claim Workflow

### Sequence
```
[claim received]
   │
   ▼  FNOL Handler DW                                   (Meridian · DW-1)
   ├ claim-intake          (gpt-4o + Fabric POLICYHOLDER_HISTORY + Foundry PAC-INTAKE)
   ├ coverage-verification (Foundry PAC-COV-001/002 + PAC-REG-001)
   ├ initial-triage        (Foundry PAC-TRI-001 + Fabric SIMILAR_CLAIMS + Fabric SEVERITY_DIST + Work IQ TEAMS_THREAD)
   └ assignment-routing    (Foundry PAC-ROUTE-001 + tool.adjuster-roster + Work IQ CALENDAR_SIGNAL)
   │
   ▼  Damage Handler DW                                 (Meridian · DW-2)
   ├ damage-intake
   ├ damage-categorization  ← can trip gate.total-loss-suspect (field-value HITL)
   ├ repair-estimation      ← cites Fabric INCIDENT_MIX/state + vehicle-history
   └ shop-routing
   │
   ▼  Fraud Handler DW                                  (Meridian · DW-3)
   ├ fraud-intake
   ├ fraud-pattern-scan     ← cites 3 Fabric primitives at once (SIMILAR + HOUR_OF_DAY + INCIDENT_MIX)
   ├ fraud-score            ← can trip gate.priority-fraud-review (mandatory HITL)
   └ siu-routing
   │
   ▼  Settlement Handler DW                             (Meridian · DW-4)
   ├ settlement-intake
   ├ settlement-calculation ← can trip gate.high-value-settlement (>$25K, field-value)
   ├ settlement-disclosure  ← state-aware (CA/NY/TX/FL/MA/IL templates per PAC-SET-002)
   └ settlement-disbursement ← can trip gate.full-denial-review (mandatory)
```

### HITL gate semantics
- **Confidence-based:** `step.<X>.confidence < 0.6` — built into `StepRunner.EvaluateStatus`.
- **Field-value:** `step.<X>.<field> == true` or `== 'literal'` — evaluated by `HitlGateEvaluator` against agent's narrative output (keyword match in v0; structured-JSON evaluator in v1.5).
- **Resolution:** `POST /api/runs/{runId}/resolve-hitl` raises a Durable external event; orchestrator's `WaitForExternalEvent` resumes with operator's choice + override.

### Runtime sequence (one step, one Function instance)
1. Console POSTs `/api/runs` → Durable client starts `FnolOrchestrator`.
2. Orchestrator calls `PrepareRunActivity` → loads bundled package zip + claim corpus.
3. For each agent: `RunStepActivity` → `StepRunner.RunStepAsync`:
   - Resolves intent + dimensions + sourceBindings from `ContextBinding`.
   - `ContextRouter.GetContextAsync` fans to all 3 L5 sources in parallel.
   - `IAgentAdapter.InvokeAsync` calls LLM (gpt-4o via Foundry Agent Service [code ready] or legacy AOAI [active cloud default]).
   - Tool calls dispatched through `IndustryAwareToolRegistry` to the right industry's kit.
   - `HitlGateEvaluator` checks confidence + field-value triggers.
4. `CompositeDecisionSink` writes the step event to Cosmos (`dw-state`) + pushes to SignalR (`fnoltrace` hub keyed by `subjectId`).
5. If status = `needs-human-review`: orchestrator `WaitForExternalEvent("HitlResolution", 30min)`. Otherwise: next agent.
6. After last agent: orchestration completes; final trace queryable via `/api/traces/{subjectId}`.

## 8. Honest gaps + v1.5 backlog

What v1.0 is NOT, deliberately:
- **Foundry Agent Service runtime is dormant.** Code ready; 2 RBAC role assignments pending. Function stays on the legacy AOAI chat-completions adapter until granted. ADR-0013 has the activation script.
- **Microsoft Graph Work IQ requires manual tenant seeding.** Code path tested; demo signal only meaningful if the deployer creates Outlook/OneDrive/Calendar content referencing claim IDs. Cloud stays synthetic.
- **Power BI semantic model with named DAX measures is v1.5.** Today's Fabric IQ uses SQL aggregation primitives over the default semantic surface — functionally equivalent for agent context but doesn't unlock Copilot-for-PowerBI or cached measures.
- **Defender for AI + Sentinel + Purview** — wiring is documented in ADRs 0007/0008 but the Entra Agent ID propagation through trace records is a v1.1 follow-on after Foundry runtime activates.
- **Decision Ingest as a Container Apps service** — today's cloud path uses `CompositeDecisionSink` directly to Cosmos + SignalR; the Event Hubs consumer is CLI-only (`adpc ingest`). v1.5 promotes it to a Container App.
- **Real backends for MCP tools** — synthetic data drawn from ambient claim/application. v1.5 swaps for Duck Creek / J.D. Power / ISO ClaimSearch / tri-bureau adapters.
